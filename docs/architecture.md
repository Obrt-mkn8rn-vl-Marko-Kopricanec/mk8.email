# mk8.email architecture

mk8.email is split into a continuously available presentation plane and an independently deployable application plane.

## Runtime boundary

- **Gateway** owns every network listener and presentation concern: TLS, HTTP, JMAP, DAV, OAuth endpoints, SMTP, IMAP, POP3, ManageSieve, protocol parsing, response rendering, connection lifetime, and durable inbound/outbound traffic recording.
- **Application Worker** owns email and groupware use cases and domain policy. It consumes durable requests, publishes durable responses, and remains dormant on PostgreSQL `LISTEN` while no work is available. It must not reference ASP.NET Core or expose a network API.
- **Contracts** contains transport-neutral request, response, journal, storage, and outbound-mail operation contracts. It has no ASP.NET Core, Entity Framework Core, Npgsql, or Azure SDK dependency.
- **MailWire** contains bounded line reading, OAuth SASL parsing, connection limiting, POP3 wire and IMAP modified UTF-7 mailbox-name encoding, and SMTP address, DSN, and wire-encoding helpers without application or database dependencies.
- **Messaging** implements the encrypted PostgreSQL control plane. Requests survive an absent worker, are claimed with leases and `FOR UPDATE SKIP LOCKED`, and use PostgreSQL notifications only as wake-up hints; durable state remains authoritative.
- **Messaging** also exposes a protocol-neutral, fail-closed byte-stream recorder for Gateway-owned raw listeners. Each read and write is assigned a durable traffic-session sequence before the protocol handler proceeds.
- **Storage** implements the large-object data plane through the Azure Blob Storage protocol. The adapter accepts an injected `BlobServiceClient`, so production can target Azure or mk8.sava's Azure Blob-compatible endpoint without leaking an Azure SDK dependency into Application logic.

Gateway and Application Worker may use different hosts. They share only the PostgreSQL messaging database, the configured Azure Blob-compatible object store, compatible encryption keys, and the contracts assembly.

## Payload persistence

PostgreSQL stores queue state, immutable object references, lengths, ciphertext SHA-256 digests, encryption metadata, and small control envelopes. Payloads over the configured inline threshold are encrypted with AES-256-GCM before upload and are stored only through the Azure Blob protocol. The database constraint permits either an inline ciphertext or an `azure-blob` reference, never both.

Object writes are conditional and immutable. Reads are constrained to the recorded ETag and verified against the recorded length and ciphertext digest before authenticated decryption. A missing, replaced, truncated, or tampered object fails closed.

Message metadata is authenticated as AES-GCM associated data but remains visible in PostgreSQL. Callers must keep credentials, message bodies, attachments, and other secrets in the encrypted payload, not in metadata.

JMAP upload blobs now follow this boundary as reference-only rows. Application Worker externalizes legacy inline uploads before it begins consuming requests, serializes that migration across hosts, and then enables a PostgreSQL constraint that forbids inline JMAP blob bytes. Account quota updates use PostgreSQL advisory transaction locks, while object deletion follows the enclosing JMAP method's commit or rollback outcome.

Raw mail queue messages, including their MIME attachments, also use reference-only Azure Blob-compatible objects. A serialized startup migration preserves legacy rows before enabling a database constraint that forbids inline queue content. SMTP and JMAP submission upload the immutable object before committing queue metadata, queue processing verifies its length and SHA-256 digest, and retention cleanup deletes the object only after the corresponding row deletion commits. PostgreSQL notifications wake the queue worker for new or rescheduled work; the bounded fallback exists only to recover missed notifications and expired leases.

Production mail smokes tag inbound probes with a DSN envelope ID and locate queue rows by that metadata rather than searching raw message bytes, which are no longer in PostgreSQL. The quarantine smoke invokes a narrowly scoped Application maintenance operation that verifies the marker, sender, state, stored header, and immutable object name before removing a test row and its matching Blob. A failed Blob deletion fails the smoke instead of reporting a clean quarantine test.

While a claimed queue message is being scanned or delivered, its PostgreSQL lease is renewed through a separate database context. If renewal fails or ownership changes, the worker cancels ongoing delivery and will not overwrite the new owner's queue state.

CalDAV and CardDAV resource bodies now use reference-only Azure Blob-compatible objects as well. The shared storage service verifies every read against the PostgreSQL length and SHA-256 digest, and DAV and JMAP Contacts writes share commit-aware replacement and deletion cleanup. A serialized startup migration externalizes legacy resource bytes before enabling a database constraint that forbids inline DAV bodies; it runs for DAV or JMAP Contacts deployments because both protocols share the same resources.

Stored mailbox messages, including MIME attachments, also use reference-only Azure Blob-compatible objects. The Application Worker externalizes legacy inline mailbox bodies before serving requests, verifies length and digest on reads, and enables a database constraint that forbids inline bodies.

## Availability semantics

PostgreSQL `LISTEN`/`NOTIFY` wakes the independent Wake process, not Application; a bounded fallback scan recovers missed notifications and expired leases. The standalone Worker accepts `--prepare` for schema creation, seeding, and legacy Azure Blob migration during activation or after an upgrade has stopped the old path/drain. Routine `--drain` launches do none of that preparation: they claim and process existing application requests and due mail queue entries, run the JMAP push batch when enabled, check twice for newly arrived work, and exit when currently due work is exhausted. The split-host activation path starts that Worker through a systemd path only when Wake signals durable work. A separate daily timer starts the same one-shot drain for completed-mail queue and Blob retention cleanup even if no new mail arrives. The prior resident `--serve` unit remains installed but must be inactive; privileged operational validation remains before this is an approved production scale-to-zero deployment.

`mk8.email.Wake` is the independent wake-side process under construction. It references Npgsql but no Application, Gateway, ASP.NET, or Blob SDK assembly. Its PostgreSQL probe checks due application requests, mail retries and expired leases, JMAP push retries/expiry, and changes missed while it was offline; it returns the next scheduled wake instant. The monitor listens to all three notification channels, also rechecks on a bounded timeout, and creates one idempotent file in a configured local trigger directory for the systemd path unit. It reads only a dedicated database connection-string file, not Worker configuration or Blob credentials. Before either probing or monitoring, it requires SELECT only on the scheduling columns of eight tables and rejects whole-table SELECT, sensitive or unrelated column access, elevated or inherited roles, write privileges, schema creation, and callable security-definer functions. PostgreSQL coverage exercises the probe with a restricted role. The `mk8email-wake.service` and `mk8email-worker.path` units are installed disabled with a dedicated OS-only `mk8wake` identity. The path targets a separate `mk8email-worker-drain.service`: its privileged fixed-path pre-start removes the consumed trigger before `--drain`, allowing a new trigger to survive until the path is rechecked after process exit. No wake connection secret is created or service started by installation.

Neither PostgreSQL notifications nor an in-process connection is required for correctness. A Gateway can enqueue while every Application Worker is offline, and a later worker on another machine can claim and complete the request.

A PostgreSQL/Azurite process-boundary regression prepares the database with the Worker owner's configuration, then starts the production-mode Gateway with a separate configuration file and a restricted PostgreSQL role that cannot read Application tables or create schema. With no Worker process, Gateway remains live and transport-ready, records both directions of an unauthenticated JMAP exchange, completes and journals a reverse WebPush validation request, and queues an end-to-end health request. The production Wake executable uses a third, scheduling-column-only PostgreSQL account with no Worker configuration or Blob connection string; Wake finds the queued request and emits the path trigger before a separate one-shot Worker executable completes it. The same test exercises the container-style Wake supervisor: a read-only database health probe does not start Application, while a subsequent Gateway request causes Wake to launch and await a one-shot Worker child. This proves process and credential separation, both durable traffic directions, and both Wake handoffs on a shared test backend; it does not execute the root-managed path unit or substitute for a two-host production outage exercise.

An isolated user-systemd smoke checks the shipped path/drain unit's trigger and pre-start directives, then uses an unprivileged transient unit pair to prove that a second signal written during a running drain causes one more activation after the first exits. It does not execute the root-managed production units or their sandbox and therefore cannot replace the privileged host smoke.

`mk8.email.Application.Worker` is the ASP.NET-free executable for this role. It validates only worker-owned configuration, initializes the messaging schema, waits on the durable request channel, creates one dependency-injection scope per claimed operation, renews leases while work is active, and publishes a durable response or sanitized failure. Its typed operation set covers administration, authentication, MFA, OAuth authorization, token lifecycle, OpenID Connect identity, JMAP email/groupware use cases, and DAV collection/resource/scheduling use cases without sharing Application assemblies or a database context with Gateway.

Gateway `/health/live` reports only the presentation process, and `/health/ready` checks the durable transport rather than requiring a running Worker. The separate, administrator-network-only `/health/application` endpoint sends the existing `system.ping` operation through the journaled Gateway-to-Worker path and reports an unavailable Worker as HTTP 503. Use this explicit end-to-end probe for activation or diagnosis, not as a prerequisite for keeping Gateway alive while a Worker is offline.

The administrator dashboard's domain/account data comes from Application through the durable request lane, while Gateway reads its own host-local operational health snapshot and composes the displayed result. Application includes only an `unavailable` status placeholder in the old dashboard wire shape so a rolling-upgrade Gateway can still decode it; Application neither depends on Gateway's `AdminConfig` nor reads a status file that would be absent on a separate Worker host.

Gateway startup does not create or migrate PostgreSQL tables and does not require a running Worker or reachable database. Its process and `/health/live` stay available during a database outage or pending snapshot restore, while `/health/ready` returns 503 and protocol traffic fails closed before presentation work can proceed. Each journal operation checks the restore marker before persisting traffic, and the reverse-presentation consumer waits for transport readiness before claiming work. Once the database and restore are ready, the same Gateway process resumes without a restart. Messaging schema creation stays on the Application Worker side; Gateway's transport control is read-only. A PostgreSQL integration test runs Gateway journal, request, reverse-presentation, and POP3 lease operations through a role with DML grants on only those control tables, no schema-create permission, and no read permission on application state. On the database host, `configure-gateway-database-access PASSWORD_FILE` provisions the restricted `mk8gateway` role after the application and messaging schemas exist. Its input must be a root-owned, mode-0600 file containing 64 lowercase hexadecimal characters; a separate, securely provisioned Gateway-readable copy is needed at the Gateway host. Set Gateway's `Database.Username` to `mk8gateway` and its `Database.PasswordFile` to that local copy; Worker keeps its schema-owning database role. The Gateway backend canary now also rejects elevated role attributes, membership, schema/database creation, access to application tables or sequences, and excess control-table grants. Neither the role password nor a live configuration is generated by the source tree.

On the database host, `configure-wake-database-access PASSWORD_FILE` opt-in provisions `mk8wake` after both schemas exist. Its input has the same root-owned, mode-0600, single-link, 64-lowercase-hex format as the Gateway role command. It gives the independent wake process only column-level SELECT on the scheduling fields of eight tables—not user password hashes or mail payloads—and refuses pre-existing privileged, unsafe column-granted, or schema-owning role state. Provision a separate Wake-readable PostgreSQL connection-string file on the Worker host with `Username=mk8wake`; do not copy Worker, Gateway, Blob, or messaging-encryption secrets into that file or the Wake service. This command installs no unit, creates no secret, and does not activate the wake process.

Native release archives and CI artifacts include standalone `worker/` and `wake/` executables beside the management `cli/` and Gateway `admin/` payloads. Split-host role controls can activate the Wake/path pair after preflight. The container build exposes distinct `worker` and `gateway` targets; the Worker-role container prepares schemas once at startup, then keeps only its small PostgreSQL Wake supervisor resident. That supervisor starts an Application Worker child in `--drain` mode only when the durable probe finds due work, waits for its exit, and rechecks. Its periodic container health probe uses Wake's restricted database connection and does not launch Application. The Worker can run on another host with the same PostgreSQL messaging and Azure Blob-compatible storage configuration. Hardened, network-capable Gateway and unprivileged Wake/drain systemd units require an explicit `/etc/mk8email/distributed-ready` marker and role-specific configuration files. None requires a local PostgreSQL service, permitting split-host operation. The single-host production installer and backup still assume a consolidated host, and an end-to-end production deployment has not been authorized.

`compose.yaml` is an opt-in container packaging example for the same two roles, not a database or object-storage deployment. It builds `gateway` and `worker` separately, starts neither through a dependency on the other, and mounts only each role's needed secrets. Its PostgreSQL and Azure Blob-compatible endpoints must already exist and be reachable from the backend network; this is why that network permits egress. Prepare the ignored `deploy/secrets/gateway_config.json` and `worker_config.json` from the distributed template with role-specific `Database.Username` and `Database.PasswordFile` (`/run/secrets/gateway_database_password` versus `/run/secrets/database_password`), shared `Messaging.EncryptionKeyFile` and `ObjectStorage.ConnectionStringFile` paths under `/run/secrets`, and the remaining role-specific secret paths named in Compose. Provision `deploy/secrets/wake_database_connection` as a separate connection string for the restricted scheduling-column PostgreSQL role; the container entrypoint uses it for Wake after `--prepare`, and the shallow health check uses it without starting Application. The container's Wake and child Worker share one non-root OS identity and mounted Worker secrets, so this example does not provide the stronger OS secret separation of the native `mk8wake` and `mk8email` units. File-backed Compose secrets are bind mounts, so ensure the container's non-root `app` user can read them without granting the Gateway access to Worker-only keys. Compose publishes only the loopback administrator port; public SMTP/IMAP/POP3/ManageSieve/JMAP ingress and production backup/rollback must be configured and verified separately. Changing this source file does not remove an existing Docker database volume.

`deploy/native/mk8email.distributed.config.example.json` is a complete configuration template, installed as `/usr/local/share/mk8email/distributed/config.example.json`. It refers to files for the shared 256-bit messaging key and Azure Blob-compatible connection string, but contains no credentials or endpoint. Gateway and Worker must use the same key and Blob namespace; their local copies may use different PostgreSQL host addresses or role-specific secret access. OAuth signing, MFA encryption, and DKIM private-key files belong only on the Worker; Gateway role validation does not read or require them. The `distributed-ready` marker must not be created until the real object-store endpoint, both role configurations, and split-service health checks are ready.

The management CLI accepts `--validate-gateway-config FILE` and `--validate-worker-config FILE` for role-specific, non-starting checks. `--probe-gateway-backends FILE` and `--probe-worker-backends FILE` additionally make a bounded PostgreSQL connection and perform an Azure Blob-compatible write/read/integrity/delete canary above the inline threshold. These probes do not create the readiness marker or start either service; `/health/application` separately verifies a live Worker through Gateway.

On a Worker-only host, `--probe-worker-dispatch FILE` sends a bounded internal `system.ping` request through the durable bus and verifies the response, so Worker execution can be checked without a local Gateway or ASP.NET listener. This internal diagnostic does not represent user protocol traffic; Gateway-originated protocol requests remain journaled by Gateway.

`activate-distributed-role gateway|worker` and `deactivate-distributed-role gateway|worker` are per-host service controls. Activation requires a non-symlink, single-link `/etc/mk8email/distributed-ready` file owned `root:root` with mode `0600`, and the selected role configuration owned `root:mk8email` with mode `0640`. It runs role validation and the PostgreSQL/Blob canary as the service account before enabling a unit. Gateway must pass its local transport readiness endpoint. Worker activation additionally requires a separate root-owned, `mk8wake`-readable connection file, starts the restricted Wake service, verifies its database canary, then enables the path and proves a real one-shot dispatch; it refuses any active or enabled resident Worker. Failed Worker activation stops and disables the path and Wake service. The consolidated production health gate checks Wake/path, but disruption recovery and privileged operational validation remain before deployment. The marker must not be provisioned until real shared backends and secrets are ready.

Worker activation runs `--prepare` before starting Wake/path. An upgrade stops the old path and drain, switches to the staged binary, prepares it, then restarts the on-demand units; preparation failure invokes binary rollback. A bare `--drain` requires previously prepared schemas and references. Binary rollback cannot reverse a partially committed database or Blob migration, so a migration-bearing release still needs a compatible forward/backward data plan and a verified backup.

For a prepared split host, `install-distributed-role ASSET_ROOT gateway|worker` installs the selected role's verified units and shared controls; the Worker choice also stages Wake, path, and drain units. It requires the exact native release and management CLI to be installed first, plus a local `mk8email` service identity and .NET runtime. It rejects unresolved deployment tokens and unsafe asset paths, refuses an active or enabled selected role, and neither creates a readiness marker nor enables or starts a service. A Gateway host separately needs its public ingress, certificates, and bindable mail interfaces; a Worker host needs its local filtering/scanner services. Both need reachable shared PostgreSQL and Azure Blob-compatible storage and the same messaging key. Provision the role-specific configuration and secrets, run the role validators and backend canaries, and activate Worker then Gateway only after those gates pass. `install-native-release ... --stage-only` validates and installs an immutable release directory without changing `/opt/mk8email/current`. `upgrade-distributed-role gateway|worker STAGED_RELEASE_ID` validates the staged role and backends before interruption, refuses a host with the other role present, atomically switches the release link, and checks the new role. The Worker branch also validates the staged Wake binary, stops path/Wake/drain together, restarts Wake then path, and proves a new one-shot dispatch; a failed upgrade attempts to restore the prior link and both units. This is binary rollback only: it does not reverse Worker schema/object migrations or shared database state, and per-host backup/restore and coordinated multi-host deployment remain required before production use.

The Worker-side management CLI now accepts `--audit-blob-references WORKER_CONFIG_PATH`. It reads all ten known PostgreSQL-backed Blob reference slots under one read-only repeatable-read snapshot, streams each referenced object through SHA-256 verification, and fails on missing, changed, incomplete, or unrecognized reference columns. It requires Worker database read access and the configured Azure Blob-compatible endpoint. The audit is a diagnostic, not a backup: concurrent deletion can still race it, and the current `mk8-backup` does not include Blob bytes or restore changed ETags. Do not treat a passing audit or the legacy PostgreSQL-only backup as split-host disaster recovery.

Production Azure Blob deletes now acquire a shared PostgreSQL advisory barrier across the physical delete. The distributed snapshot exporter takes the matching exclusive session lease *before* creating its database snapshot and holds it through Blob copying, so a snapshot-referenced object cannot disappear mid-export. Separate PostgreSQL clients exercise both lock orders, and Blob reads/writes remain available while the exclusive lease is held. The legacy `mk8-backup` does not acquire that lease or export Blobs. A long export would delay deletion-dependent request completion; retention/deferred deletion may be needed before large production backups. Direct raw-store use outside the configured services is not covered by this barrier and must not be used for mail-object deletion.

`--export-distributed-snapshot WORKER_CONFIG_PATH ABSOLUTE_DESTINATION_DIRECTORY` now produces a PostgreSQL custom-format dump and the snapshot's referenced Blob bytes in one newly created directory, with a JSONL reference manifest (format version 3, including the actual stored content types), metadata, and SHA-256 checksums. It refuses a source with an incomplete restore marker, holds the exclusive deletion lease before exporting the PostgreSQL snapshot, and passes that same snapshot to `pg_dump`; Blob bytes are streamed and verified before the directory is published. The command requires Linux, `pg_dump`, a private existing parent directory, Worker database/Blob credentials, and a new destination path; it cancels after two hours or on Ctrl-C and removes incomplete output. An isolated `pg_restore` test proves the dump and Blob manifest describe the same row even if the live row is deleted during copying. The restore marker is excluded from later snapshots so a recovered database can itself be exported and restored.

`--restore-distributed-snapshot TARGET_WORKER_CONFIG_PATH ABSOLUTE_BACKUP_DIRECTORY` verifies a complete version-2 or version-3 export before touching its target, refuses a nonempty PostgreSQL database, records a durable pending-restore marker before any Blob import, imports and reads back each Blob through the Azure-compatible API, restores the dump in a PostgreSQL transaction, and updates every referenced ETag in one serializable database transaction after checking that the restored rows exactly match the manifest. That same transaction completes the marker only when every ETag is rebound. Worker startup and backend activation probes refuse a pending target; Gateway stays live but unready and rejects protocol work until completion. Use a newly provisioned database and dedicated target Blob container/prefix; keep public ingress isolated and Wake and Worker stopped until the command, a post-restore Blob-reference audit, and protocol smoke all pass. An already-running Gateway can remain live, but completion of the marker alone does not authorize reopening ingress. A failed operation can leave imported Blobs or a restored database with old ETags; it remains activation-blocked and must be reprovisioned before retrying. The restricted Gateway database role needs SELECT on only `mk8_restore_state.state` after restore; rerun `configure-gateway-database-access` before activation. These commands are still not the production backup system: the legacy timer does not invoke them, database globals and per-host configuration are not captured here, and encrypted off-host retention plus coordinated multi-host recovery remain required. Large exports can delay deletion-dependent responses while holding the barrier.

`--verify-distributed-snapshot ABSOLUTE_BACKUP_DIRECTORY` checks archive structure, every file checksum, manifest row/count integrity, and Blob byte lengths without database or Blob credentials. It reports the archive format and reference counts but does not replace an isolated restore, a destination Blob audit, or encrypted off-host retention. A real CLI process regression accepts v2 and v3 and rejects a tampered Blob before any restore begins.

The opt-in `mk8-distributed-backup WORKER_CONFIG BACKUP_ROOT DOTNET_EXECUTABLE CLI_DLL` wrapper creates a timestamped local snapshot candidate on a Worker-capable host. It requires a canonical, mode-0700 backup root owned by its unprivileged caller, serializes runs with a private lock, exports into a private staging directory, invokes the offline verifier, and atomically publishes only after both commands succeed. Failed export or verification leaves no published candidate. If the system `pg_dump` is unsuitable, set `MK8EMAIL_PG_DUMP_EXECUTABLE` to an absolute path to the matching installed PostgreSQL client binary; otherwise the CLI uses `pg_dump` from `PATH`. The wrapper does not install or enable a timer, delete old backups, capture PostgreSQL globals or host configuration, encrypt or copy the result off-host, or replace the legacy `mk8-backup`; those are separate release gates. Its systemd unit and production credential path must be designed for remote PostgreSQL and Blob egress rather than inheriting the legacy localhost-only sandbox.

The separate opt-in `mk8-distributed-archive seal SNAPSHOT RECIPIENTS SIGNING_KEY VERIFY_KEY OUTPUT DOTNET CLI` command verifies a snapshot, streams a tar of its constrained file set through `age` recipient encryption, signs the ciphertext with an RSA key of at least 3072 bits using PSS/SHA-256, verifies that signature, and publishes a private sealed directory containing only `snapshot.tar.age` and its detached signature. `mk8-distributed-archive unseal ARCHIVE IDENTITY VERIFY_KEY OUTPUT DOTNET CLI` verifies the signature *before* decryption, extracts only regular files at the four registered root names and SHA-256-named Blob paths into a private staging directory, runs the offline snapshot verifier, and then publishes the recovered directory. Inputs and outputs must be canonical, caller-owned mode-0700 private directories; key and archive files must be mode 0600 and single-linked. A copied archive must have those permissions restored before unsealing. The signing private key and decryption identity are separately provisioned and never stored in the source tree or sealed artifact. Recipient encryption alone does not authenticate the archive producer, which is why the public verification key must be pinned out-of-band. This is still a local recovery candidate, not scheduled encrypted off-host retention: Azure Blob publication, PostgreSQL globals and both hosts' configuration capture, key recovery procedures, and an isolated two-host restore rehearsal remain required before replacing the legacy backup path.

The Gateway activation and periodic mail-health checks use `--healthcheck-gateway FILE` to check every enabled SMTP, IMAP, POP3, and ManageSieve socket from the Gateway-role configuration. This avoids relying on the retired combined-service configuration; HTTP transport and Worker execution have separate probes.

The five-minute shallow mail-health check verifies Wake, the path, the daily maintenance timer, and the restricted PostgreSQL role without starting Application. The explicit `--deep` check, used during activation, also sends `/health/application` through Gateway to prove a real on-demand Worker round trip. Backup-continuity smoke tracks the Wake process, path, and timer instead of expecting a permanently running Worker PID.

Disruption smoke stops the timer, path, and any active drain while leaving Gateway and Wake alive, verifies Gateway `/health/ready` remains available while `/health/application` reports an unavailable Application, then restarts the path/timer and checks queued mail recovery. Production rollback detection accepts either the prior resident Worker topology or the new Wake/path/timer topology and restores the matching frozen configuration before reactivation; neither path has yet been exercised against the real mk8.sava object store.

Gateway owns the administration UI and the complete OAuth/OIDC HTTP surface. OAuth presentation traffic is durably captured on ingress and egress even for static discovery responses and application-unavailable responses; application-bound operations also receive their own correlated encrypted request/reply records. OAuth signing and MFA encryption secrets are loaded only by Application Worker, while Gateway receives only public key material through the asynchronous control plane.

Gateway also owns the complete JMAP HTTP surface: session discovery, API requests, upload, ranged download, authentication-header parsing, response rendering, and event-source connection lifetime. The JMAP application library has no ASP.NET dependency and runs only behind typed durable operations in Application Worker. JMAP presentation requests and ordinary responses are recorded as encrypted HTTP envelopes. Event streams record the response start and every emitted SSE chunk before it is sent, while each Gateway/Application exchange is independently journaled at the internal boundary. The management CLI serves no network protocols.

JMAP Web Push delivery is requested by the Application Worker through the reverse presentation lane and performed by Gateway. PostgreSQL notifications wake the push scheduler when account state or verified subscriptions change; retry deadlines and expiry times provide timer wake-ups, with a bounded missed-notification fallback instead of a continuous database poll.

The standalone Application Worker sends outbound mail-delivery requests over the same encrypted reverse lane. Gateway owns MX resolution, outbound SMTP/STARTTLS exchanges, and fail-closed journaling of the exact application-level bytes read and written on each remote connection; large message and journal payloads use the Azure Blob-compatible data plane.

Gateway also registers the inbound SMTP, submission, and implicit-TLS listeners from the presentation assembly. SMTP sockets, TLS, command parsing, and response rendering no longer live in Application Core. Password and OAuth authentication, sender policy, local-recipient checks, and durable queue insertion cross the typed encrypted Gateway/Application request lane. Every external SMTP read/write is durably journaled before the Gateway continues; a journal write failure closes the connection before an unrecorded response is sent. The application request lane currently waits for its Worker reply, so an unavailable Worker can defer SMTP decisions or cause a temporary connection failure even while Gateway remains alive and journals traffic.

Gateway now also owns ManageSieve TCP/TLS, bounded literals, SASL framing, capabilities, and response rendering. Authenticated identity and script operations cross typed durable requests to the Application Worker; the shared traffic stream journals external byte chunks and fails closed if persistence fails. Application Core retains Sieve compilation and script policy but no longer hosts a ManageSieve listener. The legacy CLI no longer registers ManageSieve. Sieve script bodies use reference-only Azure Blob-compatible objects; a serialized Worker startup migration externalizes legacy inline scripts before a PostgreSQL constraint forbids inline content.

Gateway now owns the complete CalDAV/CardDAV HTTP surface: discovery redirects, authentication-header parsing, XML reports and properties, resource body limits, and response rendering. It forwards typed operations through the encrypted durable request lane to the ASP.NET-free DAV application assembly in Application Worker. The Gateway records each external DAV request/response and each internal Worker exchange; nginx routes DAV to Gateway port 8080. The former DAV HTTP assembly and CLI listener have been removed.

The management CLI rejects `--serve`; it only runs bounded administrative commands and health probes. POP3's listener, TLS negotiation, commands, and response rendering live in Gateway; CRLF normalization, wire-size calculation, TOP slicing, and dot-stuffing live in dependency-free MailWire. Gateway journals every external POP3 byte chunk before processing or sending it and fails closed if recording fails. Application Worker receives only typed password/OAuth authentication, INBOX snapshot, message-content read, and transactional deletion operations across the encrypted durable request lane. When an application operation is unavailable, Gateway returns a temporary POP3 error where a protocol response is still possible.

Gateway holds an atomic PostgreSQL maildrop lease per authenticated POP3 user rather than keeping an Application Worker call or database connection open for a TCP session. Every lease has a unique owner token, renews on activity, and can be reclaimed after expiry; release and renewal cannot affect a replacement owner's session. The lease is released before a successful QUIT response so another Gateway session can acquire the maildrop immediately. A real TLS-to-PostgreSQL-to-Worker transport test covers separate Gateway and Worker connections, concurrent maildrop locking, encrypted journal records, and typed backend operations. This branch remains non-deployable until real shared Blob storage, split-service operational smoke, backup continuity, deployment rollback, and final independent review pass.

IMAP password and IMAP-scoped OAuth authentication are typed Worker operations, shared by the presentation listener and the durable request dispatcher. The IMAP listener, MIME section rendering, TLS, bounded command parsing, and response framing now live in `mk8.email.Imap.Presentation`, hosted by Gateway. Application Core no longer compiles an IMAP socket listener or references its presentation MIME formatter. Gateway supplies a durable, fail-closed raw-byte traffic journal to the listener before the TLS layer. The management CLI cannot host this listener.

IMAP mailbox enumeration for LIST and LSUB is also a typed Worker operation. Application returns only owned mailbox metadata and primary/subscription flags; presentation code constructs hierarchy entries, applies IMAP patterns, and renders response lines.

STATUS and LIST-STATUS request structured mailbox state through one batched Worker operation. The shared Application-side resolver retains owner-scoped primary and qualified-alias lookup; the presentation listener requests only the counts it needs and formats IMAP status items. SUBSCRIBE and UNSUBSCRIBE use an owner-scoped Worker mutation with idempotent state changes. CREATE, RENAME, and DELETE validate and mutate mailboxes in the Worker, returning typed outcomes and mailbox identity where needed. RENAME updates the mailbox subtree in a serializable transaction; DELETE coordinates its serializable database commit with Azure Blob-compatible message-object cleanup. SELECT and EXAMINE receive an owner-scoped mailbox snapshot, including flags, first-unseen position, and optional QRESYNC deltas, from the Worker under a repeatable-read transaction. GETQUOTA and GETQUOTAROOT read account usage and limit through one typed Worker operation. IDLE requests owner-scoped, repeatable-read mailbox snapshots from the Worker; Gateway retains the timer, connection, diff rendering, and recovery from transient Worker outages. Message mutations, APPEND, SEARCH, SORT, THREAD, and paged FETCH are typed Worker operations. Each FETCH page is repeatable-read internally; a high-water UID and message count are carried across pages. If an expunge shifts sequence numbers between pages, the Worker rejects the later page and Gateway terminates that command with a tagged temporary failure instead of sending misleading sequence numbers. This is protocol-safe drift detection, not a promise that all mutable flags are frozen across the entire command.
