# Enterprise compatibility scope

## Outlook mail discovery

Gateway accepts POX XML `POST /autodiscover/autodiscover.xml` over HTTPS. The request must use Microsoft's Outlook request namespace, include a valid `EMailAddress`, and request the `2006a` Outlook response schema. Registered field order, namespaces, uniqueness and scalar shape are checked. DTDs and external entities are prohibited; both HTTP capture and XML parsing have a 64-KiB budget. Microsoft specifies the [request structure](https://learn.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-oxdscli/3fe8d69b-faf4-48f0-bd55-792d8ade90c0) and [response schema identifier](https://learn.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-oxdscli/def6989b-5838-421e-9498-38ada3e258b3).

This first implementation requires HTTP Basic authentication over TLS. Gateway forwards credentials through the existing typed, encrypted durable Application transport; Worker retains the existing password/application-password, MFA and account policy. The requested address must match the authenticated primary username and an owned mailbox. Alias-only, foreign-account and LegacyDN discovery are not supported. A request address or HTTP `Host` header cannot grant mailbox authority or select a mail server.

Successful responses use configured `Smtp.Hostname` and advertise only enabled implicit-TLS IMAP, POP3 and SMTP submission listeners, with their configured ports, authentication required, SSL on and SPA off. Microsoft defines these [mail protocol types](https://learn.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-oxdscli/48d23e06-f884-44b5-993e-75b7a115827c) and the [SPA flag](https://learn.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-oxdscli/9843e499-c0e0-4ab4-8bff-7f8331c6a26d). STARTTLS-only listeners, unauthenticated server-to-server SMTP and nonexistent Exchange services are never substituted. If no supported implicit-TLS listener is enabled, discovery returns error 501 without settings.

GET returns XML error 600; HEAD returns its headers without a response body. Malformed requests use 600, unsupported schemas or LegacyDN-only lookup use 601, authenticated account mismatches use 500, and sanitized internal/unavailable failures use 603. Authentication failure additionally returns HTTP 401 with a Basic challenge; plain HTTP is refused with HTTP 403, and oversized bodies with HTTP 413. These XML codes follow Microsoft's [Autodiscover error definitions](https://learn.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-oxdscli/713ef4f4-83b2-4375-9d64-60c97ee5b166).

Presentation, parsing and rendering stay in Gateway. This adds no ASP.NET dependency to Application, no new Worker operation and no queue schema change. All accepted casing/trailing-slash aliases share the original durable inbound/outbound capture boundary and remain separate from administrative error pages/network restrictions. A journal failure withholds account settings and fails closed; it cannot promise a durable record when persistence itself is unavailable. Requests and responses are not cached.

Local regressions exercise the Production HTTP pipeline and real Kestrel TCP peers, encrypted PostgreSQL transport/journaling, Azure Blob externalization and an actual Worker loop with controlled authentication/mailbox results. Separate Application tests cover real credential policy. The HTTP fixture uses trusted proxy TLS metadata; it does not certify public TLS, DNS, mail-listener availability or an actual Outlook client. No client-version interoperability claim is made.

DNS, certificate provisioning and reverse-proxy exposure of an Autodiscover hostname remain operational work. The endpoint alone does not establish automatic discovery for a hosted domain; current Thunderbird autoconfiguration is independent. No live configuration is changed by this source implementation.

## Remaining native Exchange implementation

The enterprise target is larger than mail discovery or Thunderbird compatibility. Native Exchange account support still needs MAPI/HTTP and ROP mailbox/directory operations, EWS, Exchange ActiveSync, OAB/GAL discovery and synchronization, cached Exchange behavior, and the corresponding rich-item, sharing and delegation semantics. Those services are not currently implemented or advertised. This discovery foundation must not be described as complete native Exchange compatibility.

All attachments and large objects continue through the Azure Blob Storage protocol. Local Azurite coverage does not demonstrate interoperability with the actual mk8.sava endpoint. Source review, exact artifact identity, owner acceptance and the existing certificate, split-host recovery, independent secret reissue/rotation and production-readiness gates remain prerequisites to deployment.
