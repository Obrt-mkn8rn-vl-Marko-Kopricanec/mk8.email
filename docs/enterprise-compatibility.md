# Enterprise compatibility scope

## Outlook mail discovery

Gateway accepts POX XML `POST /autodiscover/autodiscover.xml` over HTTPS. The request must use Microsoft's Outlook request namespace, include a valid `EMailAddress`, and request the `2006a` Outlook response schema. Registered field order, namespaces, uniqueness and scalar shape are checked. DTDs and external entities are prohibited; both HTTP capture and XML parsing have a 64-KiB budget. Microsoft specifies the [request structure](https://learn.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-oxdscli/3fe8d69b-faf4-48f0-bd55-792d8ade90c0) and [response schema identifier](https://learn.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-oxdscli/def6989b-5838-421e-9498-38ada3e258b3). Requests and responses use [UTF-8 as required by the POX reference](https://learn.microsoft.com/en-us/exchange/client-developer/web-service-reference/user-pox); invalid UTF-8, non-UTF-8 wire encodings and contradictory encoding declarations are refused.

This first implementation requires HTTP Basic authentication over TLS. Gateway forwards credentials through the existing typed, encrypted durable Application transport; Worker retains the existing password/application-password, MFA and account policy. The requested address must match the authenticated primary username and an owned mailbox. Alias-only, foreign-account and LegacyDN discovery are not supported. A request address or HTTP `Host` header cannot grant mailbox authority or select a mail server.

Successful responses use configured `Smtp.Hostname` and advertise only enabled implicit-TLS IMAP, POP3 and SMTP submission listeners, with their configured ports, authentication required, SSL on and SPA off. Microsoft defines these [mail protocol types](https://learn.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-oxdscli/48d23e06-f884-44b5-993e-75b7a115827c), [mail connection fields](https://learn.microsoft.com/en-us/exchange/client-developer/web-service-reference/protocol-pox) and the [SPA flag](https://learn.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-oxdscli/9843e499-c0e0-4ab4-8bff-7f8331c6a26d). STARTTLS-only listeners, unauthenticated server-to-server SMTP and nonexistent Exchange services are never substituted. If no supported implicit-TLS listener is enabled, discovery returns error 501 without settings.

GET returns XML error 600; HEAD returns its headers without a response body. Malformed requests use 600, unsupported schemas or LegacyDN-only lookup use 601, authenticated account mismatches use 500, and sanitized internal/unavailable failures use 603. Authentication failure additionally returns HTTP 401 with a Basic challenge; plain HTTP is refused with HTTP 403, and oversized bodies with HTTP 413. These XML codes follow Microsoft's [Autodiscover error definitions](https://learn.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-oxdscli/713ef4f4-83b2-4375-9d64-60c97ee5b166).

Presentation, parsing and rendering stay in Gateway. This adds no ASP.NET dependency to Application, no new Worker operation and no queue schema change. All accepted casing/trailing-slash aliases share the original durable inbound/outbound capture boundary and remain separate from administrative error pages/network restrictions. A journal failure withholds account settings and fails closed; it cannot promise a durable record when persistence itself is unavailable. Requests and responses are not cached.

Local regressions exercise the Production HTTP pipeline and real Kestrel TCP peers, encrypted PostgreSQL transport/journaling, Azure Blob externalization and an actual Worker loop with controlled authentication/mailbox results. Separate Application tests cover real credential policy. The HTTP fixture uses trusted proxy TLS metadata; it does not certify public TLS, DNS, mail-listener availability or an actual Outlook client. No client-version interoperability claim is made.

DNS, certificate provisioning and reverse-proxy exposure of an Autodiscover hostname remain operational work. The endpoint alone does not establish automatic discovery for a hosted domain; current Thunderbird autoconfiguration is independent. No live configuration is changed by this source implementation.

## EWS primary-account mail folders

Gateway accepts SOAP 1.1 `POST /EWS/Exchange.asmx` with `text/xml`, strict UTF-8 or BOM-marked UTF-16, and HTTP Basic credentials over TLS. SOAP namespaces, registered element order/attributes/cardinality, schema-version headers, body/action agreement and supported property paths are validated. DTDs/external entities are prohibited. Processing instructions are rejected throughout the document, including scalar values and opaque optional headers. Unknown mandatory SOAP headers fail with `MustUnderstand`; impersonation is rejected, and no JMAP bearer scope is repurposed as EWS authority. Optional unknown headers cannot supply an account identity. This follows the [SOAP 1.1 envelope/header/fault binding](https://www.w3.org/TR/2000/NOTE-SOAP-20000508/) and Microsoft's [RequestServerVersion](https://learn.microsoft.com/en-us/exchange/client-developer/web-service-reference/requestserverversion) schema-version contract; no Microsoft server/product version is invented.

The initial [GetFolder](https://learn.microsoft.com/en-us/exchange/client-developer/web-service-reference/getfolder-operation) and [FindFolder](https://learn.microsoft.com/en-us/exchange/client-developer/web-service-reference/findfolder-operation) implementation covers the authenticated primary account's **mail folders**. `msgfolderroot` is a virtual mail-hierarchy root, not the higher mailbox `root` containing calendars/contacts. Distinguished inbox/sentitems/drafts/deleteditems/junkemail resolve existing domain roles, including renamed role-bearing folders. A `Mailbox/EmailAddress` must match the authenticated primary SMTP address; proxy aliases, secondary/shared mailboxes, delegation and foreign accounts do not grant settings or folder authority. Versioned opaque IDs include account and folder identity but are not credentials. Worker independently reauthorizes the account for every typed operation. The [DistinguishedFolderId contract](https://learn.microsoft.com/en-us/exchange/client-developer/web-service-reference/distinguishedfolderid) requires primary SMTP, not a proxy address.

`IdOnly` and `Default` folder shapes support additional `folder:FolderId`, `ParentFolderId`, `FolderClass`, `DisplayName`, `TotalCount`, `ChildFolderCount` and `UnreadCount` paths. Mail folders use `IPF.Note`; counts/names/parents come from the same production folder model used by JMAP. Response properties follow the [Folder schema order](https://learn.microsoft.com/en-us/exchange/client-developer/web-service-reference/folder). ChangeKeys conservatively track the account's folder state. Per-reference failures remain distinct from successful batch entries.

Bounded [CreateFolder](https://learn.microsoft.com/en-us/exchange/client-developer/web-service-reference/createfolder-operation), [UpdateFolder](https://learn.microsoft.com/en-us/exchange/client-developer/web-service-reference/updatefolder-operation) and [DeleteFolder](https://learn.microsoft.com/en-us/exchange/client-developer/web-service-reference/deletefolder-operation) reuse the existing typed Worker folder mutation service. Creates support generic mail folders and an optional `IPF.Note` class; updates support only `SetFolderField` for `folder:DisplayName`; deletes support only `HardDelete` of ordinary leaf folders, including their contained messages. Protected role folders, the virtual root, non-leaf deletion, non-mail classes, other fields, soft deletion and MoveToDeletedItems are refused, not simulated. Names are NFC-normalized and remain subject to the shared folder-name and sibling-uniqueness rules. IDs remain stable across rename, successful creates/renames return ID and current ChangeKey, and individual write outcomes retain input order. An optional supplied ChangeKey must be canonical base64 and match the account snapshot; even without one, the Worker atomically checks that snapshot before writing. PostgreSQL account-row coordination covers folder and message writers so concurrent changes cannot authorize a write against an obsolete snapshot. This is deliberately conservative account-wide conflict detection, not fine-grained Exchange item-version semantics.

Shallow and deep traversal exclude the selected parent and order by leaf display name with deterministic ID tie-breaking. Forward indexed paging (`BasePoint=Beginning`) supports a nonnegative offset and at most 100 returned folders per parent. Requests are limited to 32 references, a 64-KiB body, and an account hierarchy of at most min(500, Worker `MaxObjectsInGet`, conservative encoded-envelope capacity) folders. The capacity reserves shared metadata and the authenticated profile, then 4 KiB per fixed typed snapshot; it applies even with JMAP HTTP disabled. An initial typed count query refuses oversized hierarchies before requesting an encoded snapshot. Count/state disagreement fails with `ErrorServerBusy`, not an inconsistent page; overflow or unpaged results beyond 100 return `ErrorExceededFindCountLimit` without partial folders. A rendered SOAP batch exceeding the durable response-envelope budget becomes a recorded `ErrorDataSizeLimitExceeded` fault before emission. AllProperties, extended/arbitrary properties, restrictions, fractional/backward paging, soft-deleted traversal and non-mail stores are unsupported rather than simulated. [IndexedPageFolderView](https://learn.microsoft.com/en-us/exchange/client-developer/web-service-reference/indexedpagefolderview) defines backward seeking separately; this slice rejects it explicitly.

Casing/trailing-slash aliases share the Production durable capture boundary. Inbound requests/rejection metadata and final SOAP responses are appended before emission; persistence failure withholds folder data and fails closed. TLS/authentication, capture limits, sanitized unexpected failures and application availability failures use SOAP rather than administrative HTML. Responses are `no-store`; HEAD has no body. These development-environment routes are **not yet advertised in POX Autodiscover**, and installed reverse-proxy/DNS/public TLS exposure is separate operational work.

Local coverage uses real Production/Kestrel peers, encrypted PostgreSQL/Azure journal and transport, an actual Worker dispatcher and production relational folder/profile/receipt services. Credential issuance and trusted proxy TLS metadata are controlled fixture inputs, not live credential/certificate or Outlook interoperability evidence. Bidirectional HTTP JMAP/EWS visibility exercises shared folder identity and state; no separate Exchange store is introduced. Application and Worker remain ASP.NET/XML-free, and the existing queue contract is unchanged. The additive runtime schema installs account-coordination triggers on folders/messages without rewriting existing data. Typed folder snapshots and initial state baselines use the same coordination, preventing an initial baseline from masking an uncommitted older delta. A failed outbound journal append withholds the success acknowledgement; it cannot undo an already committed Worker mutation, which remains subject to existing durable receipt/replay semantics.

Mail write coordination uses a transaction-scoped exclusive PostgreSQL advisory gate before account, folder, message and receipt row locks. Every Npgsql `EmailDbContext` transaction enters this gate at transaction start; saves without an existing transaction enter before collecting persisted message scope and JMAP changes. Database BEFORE STATEMENT guards also admit direct folder/message/inbox writes and parent deletes before row/cascade locking. Existing folder SHARE and account locks remain in place. The two-integer MK8F:1 key is separate from the existing bigint receipt/Blob/DAV lock namespace. This consistent order prevents the opposing folder/account lock cycle without replaying complete transactions or weakening deletion/scope protection; see PostgreSQL's [locking guidance](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS).

This is intentionally coarse, database-wide serialization of these domain transactions, including across accounts. It does not serialize Gateway's independent raw PostgreSQL transport/journal connections, and it is not a throughput or arbitrary privileged-SQL deadlock-freedom guarantee. Manually attached transactions and direct SQL that pre-acquire other locks must obey the same gate-first order. Finer-grained coordination remains a separate reviewed optimization. Regression controls exercise the actual typed rename/delete with an overlapping SQL/EF message writer, retain a deliberately disabled-guard deadlock control, and cover parent cascades, stable delta scope, cancellation/context reuse, synchronous EF use and additive guard repair.

Install or repair the coordination DDL only while domain writers are quiesced under the existing coordinated-upgrade procedure. Do not mix old Worker binaries lacking gate-first transaction interception with the new coordination schema as a rolling upgrade. Gateway's independent recording can remain live; this does not waive stopped business admission, exact-release validation or the privileged upgrade/rollback gates. The repair regressions demonstrate additive, idempotent metadata repair, not online DDL safety against arbitrary prelocked direct-SQL sessions.

## EWS primary-account mail-item metadata

The first `GetItem` profile supports `IdOnly` plus explicit additional metadata properties: `item:ItemId`, `ParentFolderId`, `ItemClass`, `Subject`, `DateTimeReceived`, `Size`, `IsDraft`, `DateTimeSent`, `HasAttachments`, and `message:Sender`, `ToRecipients`, `CcRecipients`, `BccRecipients`, `From`, `InternetMessageId`, `IsRead`, `ReplyTo`. It uses the same authenticated primary-account selection and typed, independently reauthorized Worker message reader as JMAP, with Azure Blob-backed stored MIME. SOAP/XML and MIME presentation remain in Gateway. See Microsoft's [GetItem contract](https://learn.microsoft.com/en-us/exchange/client-developer/web-service-reference/getitem-operation), [ItemShape order](https://learn.microsoft.com/en-us/exchange/client-developer/web-service-reference/itemshape) and [Message property order](https://learn.microsoft.com/en-us/exchange/client-developer/web-service-reference/message-ex15websvcsotherref).

Item IDs are canonical versioned opaque identifiers in a namespace separate from folder IDs. They include account identity but grant no authority. Foreign-account IDs are refused; rewrapping a foreign message ID with the authenticated account yields not-found through Worker authorization. Batch results retain input order and repeated references, with per-reference malformed, foreign and missing outcomes. Current ChangeKeys conservatively track account-wide email state; canonical supplied read keys do not make the read conditional. Parent-folder IDs do not reuse the email ChangeKey. Requests have the existing 64-KiB capture/XML budget and at most 32 references, additionally respecting Worker object limits. Shared encoded transport/journal and final SOAP budgets remain enforced; data is withheld on journal failure.

`Default`/`AllProperties`, raw MIME, attachment metadata/content, extended/indexed properties and recurring/non-mail item references remain explicitly unsupported. Requested Sender/From values with multiple mailboxes are refused rather than inventing a single author or silently omitting the requested value. Optional absent MIME fields are omitted. Invalid XML text or subjects beyond the conservative 255-UTF-16-unit projection bound are refused without silently changing stored mail. Default shapes, item writes, advanced search, synchronization, subscriptions and attachment retrieval remain open implementation, not advertised capabilities. GetItem itself is not automatic native Exchange account compatibility.

This source does not add EWS to the public nginx allowlist or POX advertisement, alter any deployment/queue/schema authority, or establish actual Outlook/Thunderbird/public TLS interoperability. The accepted architecture/write-coordination restrictions and all operational gates remain unchanged.

## EWS primary-account message bodies

GetItem additionally admits explicit `item:Body` with optional `BodyType` of `Best` (default), `Text` or `HTML`, in [ItemShape order](https://learn.microsoft.com/en-us/exchange/client-developer/web-service-reference/itemshape). Metadata-only shapes still send `IncludeText=false`; body shapes use the same independently authorized Worker reader with `IncludeText=true`. FindItem does not acquire body projection. No raw MIME or attachment bytes are returned by this profile.

The existing MIME display selection chooses native plain-text/HTML alternatives and excludes text attachments and related binary resources. `Best` selects HTML when the displayed representation includes HTML, otherwise text, following the [BodyType contract](https://learn.microsoft.com/en-us/exchange/client-developer/web-service-reference/bodytype). Plain text requested as HTML becomes an escaped `pre` fragment. HTML requested as text is a non-executing tokenizer projection: entities are decoded, common block/table boundaries are separated, and head/script/style/template content, comments and resource attributes are excluded. It is not a browser, CSS/layout engine or RTF renderer, and does not fetch links or resources. Unfiltered native HTML remains opaque XML text; downstream HTML display safety remains the client's responsibility. `FilterHtmlContent=false` (the [documented default](https://learn.microsoft.com/en-us/exchange/client-developer/web-service-reference/filterhtmlcontent)) is admitted; filtering requests and code-page-conversion options are explicitly refused, not falsely acknowledged.

[Body](https://learn.microsoft.com/en-us/exchange/client-developer/web-service-reference/body) is emitted in Message schema order with `BodyType` and `IsTruncated=false`, including an explicit empty body when no displayable body exists. Line endings are normalized to LF using the existing MIME projection. Selected decoding problems or XML-invalid text refuse that item without replacement or partial body content. Source and converted/combined bodies are limited to 1 MiB UTF-8 per item; overflow returns `ErrorDataSizeLimitExceeded`, never silent truncation. A repeated-reference batch can still exceed the shared final SOAP/journal envelope budget and is refused before emission. The encrypted transport/journal and Azure Blob paths remain unchanged; a transport-level failure may refuse an entire read before presentation. This is a bounded ordinary plain-text/HTML body profile, not support for every rich/encrypted/signed MIME layout.

Real development-environment coverage uses Production/Kestrel, the encrypted PostgreSQL/Azure journal and transport, and actual Worker authorization/receipts reading Azure-backed MIME. Controlled peers/authentication/proxy TLS and Azurite/tmpfs PostgreSQL are not actual Outlook/Thunderbird/public TLS/Sava or physical-durability certification. The larger enterprise and operational gates remain open.

## EWS primary-account item discovery

The bounded [FindItem](https://learn.microsoft.com/en-us/exchange/client-developer/web-service-reference/finditem-operation) profile discovers ordinary, non-deleted messages directly in authenticated primary-account mail folders, using the existing Worker `FindMessages` and metadata-only `ReadMessages` operations. `Traversal="Shallow"` is required. Folder identity, distinguished roles and primary SMTP checks are the same as folder reads; virtual `msgfolderroot` contains no messages and never becomes an account-wide query. Foreign IDs, primary-account wrappers around foreign folder IDs and mailbox aliases cannot supply authority. Repeated parent references retain ordered per-parent outcomes while reusing the same admitted query/read page. Discovered IDs can be consumed by the existing GetItem profile.

`IdOnly` plus explicit scalar metadata is supported: `item:ItemId`, `ParentFolderId`, `ItemClass`, `Subject`, `DateTimeReceived`, `Size`, `IsDraft`, `DateTimeSent`, `HasAttachments`, and `message:IsRead`. FindItem does not return body/MIME/attachment values or recipient lists. Sender/From, InternetMessageId and ReplyTo are explicitly refused in this initial FindItem shape; GetItem's full-address projections are not reused. Requested subjects above 255 UTF-16 units or invalid XML text produce explicit per-parent refusals, not silent truncation. See [FindItem request order](https://learn.microsoft.com/en-us/exchange/client-developer/web-service-reference/finditem).

[IndexedPageItemView](https://learn.microsoft.com/en-us/exchange/client-developer/web-service-reference/indexedpageitemview) supports nonnegative beginning offsets, an optional positive MaxEntriesReturned up to 32, and at most 32 parent references. The effective page size also respects the Worker's object limit. Results sort by received time descending, with stable stored-ID tie breaking. Beyond-end offsets return an empty final page. [RootFolder](https://learn.microsoft.com/en-us/exchange/client-developer/web-service-reference/rootfolder-finditemresponsemessage) reports the total matching count, next index and final-page flag. An unpaged result exceeding the admitted default page is refused rather than silently represented as complete. End-based/fractional/calendar/contact views, SoftDeleted/Associated/Deep traversal, restrictions/AQS, grouping, custom sort and broader item shapes remain explicitly unsupported.

Each typed query/read executes under the accepted gate-first Worker transaction boundary. Query/read email state, exact identities and direct-folder membership must agree; all parent pages share one email state, and parent graph state is rechecked before rendering the response. Concurrent committed changes produce a retryable SOAP refusal rather than a mixed page. This is bounded snapshot consistency, not an immutable cross-request cursor or throughput guarantee: offsets can shift between separate requests after mailbox changes. The shared durable capture, reply-envelope limit and append-before-send/journal-failure boundary still apply. Application remains ASP.NET/XML-free; no new queue ABI, schema, Blob provider, public proxy exposure or discovery advertisement is introduced.

## Remaining native Exchange implementation

The enterprise target is larger than mail discovery or Thunderbird compatibility. Native Exchange account support still needs MAPI/HTTP and ROP mailbox/directory operations, the remaining EWS item/folder mutation, search, synchronization, attachment and delegation families, Exchange ActiveSync, OAB/GAL discovery and synchronization, cached Exchange behavior, and corresponding rich-item/sharing semantics. Those services are not complete or advertised. Mail discovery and bounded EWS folder reads must not be described as complete native Exchange compatibility.

All attachments and large objects continue through the Azure Blob Storage protocol. Local Azurite coverage does not demonstrate interoperability with the actual mk8.sava endpoint. Source review, exact artifact identity, owner acceptance and the existing certificate, split-host recovery, independent secret reissue/rotation and production-readiness gates remain prerequisites to deployment.
